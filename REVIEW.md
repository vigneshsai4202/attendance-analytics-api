# REVIEW.md

I read the starter `app/main.py` like a pull request and ran its helper functions to check my guesses. These are the problems I found. The endpoints listed under TODO in the starter (punch-out, PATCH, analytics, explain) are the work I had to build, so I did not count them as defects.

| # | Where | What is wrong | How I noticed it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | It turns the delay into whole minutes first and then checks `minutes > 10`. So a delay of 10 min 1 sec becomes 10 and is treated as on time. The rule says late means more than 10:00 exactly, and then report the whole minutes. | Shift 09:30, punch-in 09:40:01 gave 0 when it should be 10. 09:40:00 (0) and 10:15:59 (45) looked fine, which hid the bug. | I compare in seconds (`elapsed_seconds > 600`) and only then divide by 60 and floor. |
| 2 | `compute_late_minutes` (and punch-in) | It builds the shift start with `punch_in.replace(hour, minute)` in whatever timezone the datetime is in, so on a UTC server it compares 09:30 against a UTC time. It also ignores the attendance date, so overnight shifts break. | On a UTC machine a 09:50 IST punch-in gave 0 instead of 20. For an overnight shift (22:00-06:00) a 22:25 punch-in used the wrong day. | I convert to IST and build the shift start from the attendance date plus `HH:MM` in IST, then compare aware datetimes. |
| 3 | `compute_work_hours` | It uses Python `round()` on a float. That is banker's rounding plus float error, and the rule wants half-up. | 16218 seconds is 4.505 hours. The starter gave 4.5, but it should be 4.51. | I use `Decimal(seconds) / Decimal(3600)` and round with `ROUND_HALF_UP`. |
| 4 | `compute_overtime` | There is no 30-minute minimum, so any positive minutes count as overtime. The shift end is also always on the same day, so overnight shifts are wrong. | Shift end 18:30 and punch-out 18:40 gave 10, but it should be 0. | I only count overtime when it is 30 minutes or more, and for an overnight shift I put the shift end on the next day. |
| 5 | `compute_overtime` | It subtracts a naive datetime from an aware one, which raises `TypeError`. The helper builds an aware shift end, but the starter's own timestamps (`fromtimestamp`, `now()`) are naive. | Calling it with a naive punch-out crashes with "can't subtract offset-naive and offset-aware datetimes", which would be a 500. | Everything is timezone-aware UTC inside the app, and the client uses `tz_aware=True`. |
| 6 | `punch_in` | `fromtimestamp(ms/1000)` and `datetime.now()` give naive server-local time. The date is taken from that local time, not from IST, and milliseconds are not cut off. Mongo treats naive values as UTC, so the stored time is shifted. | On a UTC server a punch-in at 00:30 IST got the previous day's date, and the stored time was off by 5h30m. | I convert epoch ms to an aware UTC datetime with the microseconds removed, and I get the date from the IST time. |
| 7 | `punch_in` | The overnight rule is missing. It just uses `ts.date()`. | An overnight employee punching in at 05:00 should belong to the previous day but did not. | A helper decides the attendance date from the shift times. |
| 8 | `punch_in` | If the employee does not exist, `emp` is `None` and `emp["shift_start"]` crashes with a 500. The contract says 404. | `{"emp_code": "EMP9999"}` | I check the employee first and raise 404. |
| 9 | `punch_in` | Race condition. It does `find_one` and then `insert_one`, with no unique index, so two requests at the same time both pass the check. | 20 parallel punch-ins gave several 201s instead of one 201 and the rest 409. | I added a unique index on `(emp_code, date)` and catch `DuplicateKeyError` to return 409. |
| 10 | `PunchInIn` / `punch_in` | `status` accepts any string, and `punched_at` has no range check, so seconds, `0` and whole-number floats get through. `if body.punched_at` also treats 0 as "not given". | `punched_at: 1783312500` (seconds) or `status: "ABSENT"` returned 201. | I use `StrictInt`, check the epoch-ms range (at least 1e11), allow only PRESENT, WFH and ON_DUTY, and test with `is not None`. |
| 11 | `punch_in` response | It returns an `id` (the ObjectId) and raw datetimes. The contract says no ids, and instants must be epoch milliseconds. | The response had `"id": "..."` and ISO strings for the punch times. | The response goes through a function that drops `_id` and turns datetimes into ms. |
| 12 | `create_employee` | No validation at all: employee code format, email, shift format, a real `joined_on` date, and `shift_start != shift_end`. | `emp_code: "x"`, `shift_start: "25:99"` and `joined_on: "string"` all returned 201. | I added Pydantic patterns and validators, so bad input gives 422. |
| 13 | `create_employee` | Same race as punch-in (`find_one` then insert, no unique index). `created_at` is also a naive `datetime.now()` returned as an ISO string, not epoch ms. | Parallel creates of the same code made duplicates, and `created_at` was not an integer. | I added a unique index on `emp_code` and return 409 on `DuplicateKeyError`. `created_at` is aware UTC and converted to ms on output. |
| 14 | `list_employees` | Off-by-one: `skip = page * page_size`, so page 1 skips the first page. `total` counts all employees and ignores the department filter. There is no sort and no limits on `page` or `page_size`. | `page=1` never showed the first employees. `?department=hr` showed the total of everyone. `page_size=100000` was accepted. | `skip = (page - 1) * page_size`, count with the same filter, sort by `emp_code`, and limit `page >= 1` and `page_size <= 100`. |
| 15 | `list_attendance` | It loads the whole collection into memory, then sorts and slices in Python. The sort is by date only, but the contract wants date descending and then `emp_code` ascending. This is fine with 9 documents but not with 100k. | Slow and heavy on memory at 100k records. Records with the same date came back in no fixed order. | Filtering, sorting, skip, limit and count all happen in MongoDB, with indexes behind the sort. |
| 16 | `list_attendance` | No validation of date format, of `date_from > date_to` (should be 422), of `status`, or of page limits. Page 0 gives negative slices. It also returns `id`, raw datetimes, and old documents without `history` or `half_day`. | `?date_from=2026-07-09&date_to=2026-07-01` returned 200, and `page=0` returned strange data. | I added validation, a `Literal` for status, a function that fills in missing fields, and a function that cleans the output. |
| 17 | `/health` | It always returns ok and never pings MongoDB. The contract wants 503 when MongoDB does not answer. | With MongoDB stopped, `/health` still returned 200. | I ping MongoDB and return 503 on `PyMongoError`. |
| 18 | whole file | There are no indexes at all: no unique `(emp_code, date)`, no unique `emp_code`, and none for the list and analytics queries. | `explain` shows `COLLSCAN`, and duplicates are possible. | `ensure_indexes()` runs at startup (safe to run again) and `/health` retries it if MongoDB was down. |
| 19 | `MongoClient(...)` | The client is not `tz_aware`, so every datetime from MongoDB is naive and gets treated as local time. | Turning a stored `punch_in` into epoch ms gives the wrong value when the server is not in UTC. | `MongoClient(..., tz_aware=True)`. |

## Things I looked at and decided were fine

- `load_dotenv()` does not override real environment variables by default, which is what the contract wants.
- `IST = timezone(timedelta(hours=5, minutes=30))` is correct. India has a fixed offset and no daylight saving.
- The starter counts late minutes from `shift_start`, not from the end of the grace period, which is what the rule says. Only the threshold check was wrong (item 1).
- The starting values on punch-in (`punch_out: None`, `work_hours: None`, `overtime_minutes: 0`, `half_day: False`, `history: []`) match the contract.
- `doc.pop("_id", None)` in `create_employee` works, because `insert_one` adds `_id` to the dict, so that response does not leak it. The punch-in response did leak it (item 11).
